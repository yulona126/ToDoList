## 2. 方案：按周迭代 + 承诺闸门

### 2.1 核心只有一条机制

> **每周只能承诺「你实测吞吐 × 1.2」条任务。超了就不让拉。**

单人敏捷里唯一真正起作用的约束是**承诺量上限**。因为你的失败模式（如果发生）不会是"看不到进度"，而是"心里同时装着 12 件事，结果只推完了 5 件"。

闸门把"velocity"从**报表**变成**约束** —— 报表没人看，约束会立刻生效。

### 2.2 数据模型：只加一列

```python
class Task(TimeStampedModel):
    ...
    # 新增：什么时候被拉进"本周承诺"
    committed_at = models.DateTimeField(null=True, blank=True, db_index=True)
```

**不新建 Iteration 表。** 迭代由时间**推导**出来，而不是手动创建：

```
本周迭代  = ISO 周（2026-W42），以 [周一 00:00, 下周一 00:00) 的区间表示
本周承诺  = Task.objects.filter(committed_at__gte=ws, committed_at__lt=we)
Backlog   = Task.objects.filter(committed_at=None)
本周吞吐  = Task.objects.filter(completed_at__gte=ws, completed_at__lt=we).count()
```

> ⚠️ **不要用 `__week` 查询。** Django 的 `committed_at__week=42` 匹配的是
> "一年中的第 42 周"，2025-W42 和 2026-W42 会被同时命中。
> 一律用**明确的日期区间**（`>= week_start` 且 `< week_start + 7d`），
> 并用 `timezone.localtime()` 取当地周边界，否则跨时区会在周一早上算错一天。

为什么要推导而不要建表：

| | 建 Iteration 表 | 用 committed_at 推导 |
| --- | --- | --- |
| 每周操作 | 手动"创建 sprint" | **零** |
| 忘记创建 | 数据空洞 | 不可能发生 |
| 结转 | 要写搬迁逻辑 | 自动：上周没做完的仍是 `committed_at != None`，进"结转"视图 |
| 迁移 | 多一张表 + FK | **一个可空列** |

> **去掉一切需要"记得做"的步骤。** 单人项目的仪式感会自动死亡。

### 2.3 三个视图（这就是全部 UI）

```
┌─ 本周 (2026-W42) ────────────────────────┐
│ 承诺 6 / 上限 6  ⚠ 已达上限               │
│                                          │
│ 待办 (4)     #152 统一错误码   高         │
│              #161 加 MCP 鉴权             │
│ 完成 (2)     ✓ #158 修 max_tokens         │
└──────────────────────────────────────────┘

┌─ 结转 (3) ── 上周承诺但没做完 ────────────┐
│ #143 接入 library 页面                    │
│  → [拉回本周]  [退回 Backlog]             │
└──────────────────────────────────────────┘

┌─ Backlog (9) ─────────────────────────────┐
│ 按工作流分组：DL (4) · IS (3) · 其他 (2)   │
│  每条右侧：[→ 拉进本周]                    │
└──────────────────────────────────────────┘
```

**没有第四列，没有拖拽，没有燃尽图。** 因为你的数据显示你不会去维护它们。

### 2.4 承诺闸门怎么算

```
上限 = round(过去 4 周完成数的中位数 × 1.2)
```

- 用**中位数**不用均值：你有批量清账的习惯，均值会被某一天的 13 条拉高
- 用**四周滑动窗**：单周数据太抖（你某天 0、某天 13）
- `× 1.2`：留 20% 弹性，纯卡死会让人绕过闸门

超限时：**允许但要求二次确认**（不是硬拦）。硬拦会被绕过，二次确认会让人停下来想一下 —— 这正是要的效果。

### 2.5 每周回顾（2 分钟，一次点击）

一条命令 / 一个按钮产出：

```
2026-W42 回顾
  承诺 6 · 完成 5 · 结转 1  → 承诺达成率 83%
  实际吞吐 5 条 · 上限 6 条
  从 Backlog 新拉入 3 条，其中 1 条当天完成（可能拆得不够细）

  下周建议上限：5 条（沿用）
```

**不生成图表。** 单人项目里，一段文字比燃烧图更有用，因为它直接给出"下周上限"这个可执行结论。

## 3. 明确不做

| 不做 | 为什么 |
| --- | --- |
| ❌ **Kanban 看板** | 你 `doing` 用了 0 次。做出来就是一排永远空的列 |
| ❌ **故事点 / 估时** | 单人、无对比、无规划用途。纯自欺 |
| ❌ **燃尽图** | 需要每天更新，你 13 条集中一天完成 —— 曲线会是台阶，没有信息量 |
| ❌ **每日站会 / 提醒** | 你是批量节奏，日频打扰只会让你关通知 |
| ❌ **Sprint 容量规划** | 单人容量 = 你自己的吞吐，不需要"规划"，只需要"上限" |
| ❌ **强制填写截止日** | 你 93% 不填，强制只会让录入变慢 |
| ❌ **Story / Epic / Feature 三层** | 你已有 Workspace + 前缀工作流，够用 |

> 这个列表比方案本身更重要。敏捷对单人最大的陷阱是**把团队的协调仪式搬到一个人身上** —— 那些仪式的成本是真实的，收益却是为零（因为不需要协调）。

## 4. 工作流前缀：正式化你已经在做的事

你的标题里已经有 `[DL005]`、`[IS-1]` 这种前缀。这是**组织自然涌现出来的工作流**，比我设计的任何字段都真实。

**不要新增字段。** 让系统识别这个前缀：

```python
# 从标题提取工作流
WORKSTREAM_RE = re.compile(r"^\[([A-Za-z][A-Za-z0-9_-]{0,15})\]\s*")
# "[DL005] 修 Detector" → workstream="DL", 标题保留原文显示
```

然后 Backlog 视图按它分组。零录入成本，零迁移。

### 过渡方案（今天就能开始，0 代码）

不想改代码的话，先跑两周验证这个节奏是否适合你：

1. 建一个标签 `w42`（本周）
2. 每周一，从待办里挑 **≤ 上周完成数** 条打上 `w42`
3. 周五看：`#w42` 里完成了多少
4. 两周后你会知道：你的真实吞吐是多少、这个节奏是否舒服

**如果两周后你觉得"这表格没意义"，那就说明你不需要这个功能 —— 别做。**
这个过渡方案是**方案本身的验证器**，比直接开发更省。

## 6. 一句话

> 所以只加一个 `committed_at`，把"这周打算做什么"从心里想着变成看得见的 —— 并且**不允许你一周接 12 件**。

## 7. 与 MCP / AI 的关系

这套周迭代天然可以接进已有的 Cursor 集成：

```
get_tasks(status="todo,doing", iteration="current")   # 本周承诺
```

于是 Cursor 整理开发计划时，拿到的是**本周真实承诺**，而不是整个 backlog。
这比上次那个"项目理解数据库"实际得多 —— 因为它直接对齐你每周的真实动作。
